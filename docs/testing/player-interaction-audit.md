## Result and method

No player-accessible ownership, revision, authentication, or busy-state bypass was found in the traced routes. I ran the plan's two searches, then read the matching callers, production registrations, service transformations, and persistence/native boundaries:

### Persistence adapters and safety invalidation

The production `setData` adapters are the Collection payload sender, CardTransfer owner and DuelManager online Players adapter. Reading their callers accounts for list/count edits, Open revalidation, login/selection revalidation and command clear. `replaceCounts` has one production caller, `CardTransferService`, which supplies planned server counts after busy/revision checks. `CollectionCommand` and its wire switch expose no replacement-count operation ([`CollectionCommand.java`](../../src/main/java/com/haxerus/duelcraft/collection/CollectionCommand.java), [`CollectionWire.java:15`](../../src/main/java/com/haxerus/duelcraft/server/collection/CollectionWire.java#L15)).

Policy-driven invalidation is an intentional exception to the edit lock: login, `/duel deck get`, `resolveDeck`, acceptance and final startup can clear an ineligible active ID without a client expected revision or idle requirement. They evaluate current server state and preserve lists/counts; no path selects a different list or grants cards. During preparation this forces final selection comparison to fail. A running engine already owns an immutable Deck snapshot, so clearing persisted activation does not rewrite that duel. The service increments the collection revision only when it clears activation; an eligible recheck preserves the revision ([`CollectionService.java:133`](../../src/main/java/com/haxerus/duelcraft/server/collection/CollectionService.java#L133)).

Development fixtures directly set attachments/inventories in `client/uitest` and `uitest`; their setup is not evidence of a production player mutation route. Session probes in `server/` enter through `decorateNextSession`, whose production guard rejects installation ([`DuelManager.java:77`](../../src/main/java/com/haxerus/duelcraft/server/DuelManager.java#L77)). They wrap manager-created sessions after its policy checks. This audit preserves these fixtures, core Deck/DeckRegistry, AI loading and native code.

## Compatibility and ownership policy

[`DuelNetworking.java:12`](../../src/main/java/com/haxerus/duelcraft/server/DuelNetworking.java#L12) registers required channel version **8**. Its five C→S routes are Interaction request, Collection request, Preparation request, Duel response and Concede. Its seven S→C routes are Interaction state, Preparation notice/state, Collection reply, Duel start/message/end. There is no `DuelDeckPayload` type/registration, old upload handler or `setPlayerCurrentDeck` route. The retained “current deck” names read/clear the collection-backed active ID; `resolveDeck` rechecks that ID. Client and server must use protocol 8; this static registration check does not claim a fresh mixed-version connection test.

Old local `.ydk` files remain available through the local registry/import path. Import carries Main/Extra/Side as a list; no migration credits deposited counts. Collection persistence remains schema 1 ([`CollectionLimits`](../../src/main/java/com/haxerus/duelcraft/collection/CollectionLimits.java), [`PlayerCollectionData`](../../src/main/java/com/haxerus/duelcraft/collection/PlayerCollectionData.java)). The registered attachment persists per player, copies on death, and has no entity tracking sync ([`CollectionAttachments.java:12`](../../src/main/java/com/haxerus/duelcraft/collection/CollectionAttachments.java#L12)). A malformed attachment retains its raw NBT and exposes unavailable data, so management cannot overwrite it with an empty collection ([`CollectionAttachment.java:13`](../../src/main/java/com/haxerus/duelcraft/collection/CollectionAttachment.java#L13)). Collections belong to the current world/server player identity.

The SERVER setting `ownership.requireCardOwnership` defaults to **false** ([`ServerConfig.java:11`](../../src/main/java/com/haxerus/duelcraft/ServerConfig.java#L11)). Loading captures the value for the server lifecycle; server startup constructs the policy with that captured value. To enable it, set `requireCardOwnership = true` in the effective `duelcraft-server.toml` and restart the server or reopen the integrated world. The [configuration contract](../superpowers/specs/2026-09-17-player-interaction-contracts.md#current-deck-use-policy-contract-2026-09-19) records the game-directory config and existing world/serverconfig override precedence; this audit does not re-test NeoForge config resolution.

[`DeckList.requiredCopies`](../../src/main/java/com/haxerus/duelcraft/collection/DeckList.java#L24) aggregates Main + Extra + Side by **exact passcode**; [`DeckEligibility`](../../src/main/java/com/haxerus/duelcraft/collection/DeckEligibility.java#L38) compares that demand with deposited counts. Inventory cards contribute only through deposit. A shortage is neutral when ownership is optional, but withdrawals still require real stored copies and available inventory capacity. Lists can share those copies without reservation or consumption; using a deck creates no physical cards.

The synchronous [`DeckUseCheckEvent`](../../src/main/java/com/haxerus/duelcraft/api/DeckUseCheckEvent.java#L25) gives a companion the authenticated owner and immutable candidate list/counts/rule. Its first denial survives later listeners. [`DeckUsePolicy.java:58`](../../src/main/java/com/haxerus/duelcraft/server/collection/DeckUsePolicy.java#L58) combines core checks with this additional denial and logs/throws on listener runtime failure. A companion cannot authorize an illegal/unowned-required deck, change busy/revision gates or grant cards through this hook. Acquisition recipes, rewards and economy remain separate companion content.

## Failure atomicity and retained limits

- Collection operations return the original data on gate rejection or policy evaluation failure. Successful mutations increment the revision once with checked arithmetic. A valid active-list edit or transfer with an ordinary denial persists the edit/transfer and clears activation; a throwing evaluator rejects it before inventory or attachment writes ([`CollectionService.java:47`](../../src/main/java/com/haxerus/duelcraft/server/collection/CollectionService.java#L47), [`CollectionService.java:100`](../../src/main/java/com/haxerus/duelcraft/server/collection/CollectionService.java#L100)).
- Transfers plan quantities/capacity and prepare replacement ItemStacks before writing inventory, then persist attachment and broadcast. They scan main slots 0–35 plus offhand 40 for deposit; withdraw fills compatible/empty main slots only. Unsupported customized or unknown deposit stacks remain intact; DepositAll reports skipped copies ([`CardTransferService.java:67`](../../src/main/java/com/haxerus/duelcraft/server/collection/CardTransferService.java#L67), [`InventoryTransferPlan`](../../src/main/java/com/haxerus/duelcraft/server/collection/InventoryTransferPlan.java)). This is rejection/policy-failure atomicity on the synchronous server thread, not a crash-safe transaction or rollback guarantee for unexpected exceptions during persistence/broadcast.
- Startup runtime failures close an installed session and remove live ownership; preparation/solo completion releases startup locks. The catch covers `RuntimeException`; this audit does not claim recovery from JVM/native failure ([`DuelManager.java:251`](../../src/main/java/com/haxerus/duelcraft/server/DuelManager.java#L251)).
- Supported player checks cover Main 40–60, Extra/Side ≤15, ≤3 per exact passcode across all sections, known playable non-token cards and Main/Extra placement. Built-in banlists, alias-group limits and full format-specific legality remain absent. The rule travels through policy but `DeckEligibility` does not implement separate Rush/Speed deck rules. Side storage/ownership checks do not add match play or sideboarding.
- Static tracing does not establish human readability, OS key rebinding, real item/offhand dispatch, or the same installed-JAR two-client/server matrix. Preserve the human multiplayer carry-forward; the [M5 playtest report](../superpowers/reports/2026-10-08-m5-playtest.md) records the user's completed non-multiplayer checks and separate UI follow-up.
